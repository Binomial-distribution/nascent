# App ↔ 后端 HTTP 接口

与 [`ble_gatt.md`](ble_gatt.md)、[`wifi_ws.md`](wifi_ws.md) 并列的第三条衔接面。
前两条是控制端与玩具之间的**控制**通道，这一条不是——它只运送**建议**。

前端与后端由不同的人维护，这个文件是两边之间的约定。改这里描述的任何形状，
都要先在这个文件里改，不要只改自己那一侧的代码。

## 这条链路不控制硬件

云端返回的是一段台词、一个情景走向、一个建议档位。建议要依次通过：

```
云端审核 → 浏览器安全总督 → 玩具侧 SafetyGovernor
```

三层里任何一层都可以否决。网络断了、云端挂了、模型胡说八道，设备该怎么工作
还是怎么工作。**这不是容灾设计，是前提。** 因此这条链路上不存在"必须成功"
的请求：前端每一处 `fetch` 都必须能在失败时静默降级，界面不能因为云端不可达
而不可用。

（0.3.0 之前这里写的是四层，中间还有一层行空板 K10 的拒绝规则。K10 已移除，
手机直连玩具侧，所以现在是三层。）

## 基址

后端用 FastAPI 同时托管 `software/app/` 里的静态页，前端与接口**同源**。
所以前端一律用相对路径 `/v1/...`，不要在页面里写死主机和端口——写死之后
换个局域网地址、或者哪天前后端分开部署，就要改一遍所有调用点。

开发期默认 `http://127.0.0.1:8000`。

## GET /v1/persona

返回可选人设列表。

响应 `200`：

```json
[
  { "id": "gentle",  "name": "温和", "tone": "缓慢、克制、多确认" },
  { "id": "playful", "name": "俏皮", "tone": "轻快、有来有回" },
  { "id": "calm",    "name": "沉静", "tone": "低语、留白多" }
]
```

**人设只决定"说什么"，不决定灯色也不决定强度。** 换人不换灯——灯只表达当前
是哪种玩法，与人设无关。所以这个对象里刻意没有任何颜色或强度字段。想往
`Persona` 里加 `color` / `level` 之前，请先回来读这一段。

### 已知契约缺口

`Persona` 是这条链路上**唯一不由 `contract.yaml` 生成**的结构，它手写在
`software/backend/app/routers/persona.py` 里，而前端 `app.js` 的 `loadPersonas()`
直接消费 `res.json()`，不做任何字段校验。

这意味着：**后端单方面改这个结构不会有任何东西报错，前端会安静地显示空白。**
现阶段骨架期先靠这份文档约束；人设一旦要落库、或者字段超过这三个，应当把它
收进 `contract.yaml`，让它和其他跨端结构一样由 `gen.py` 生成。

改它之前请同时通知前端维护者。

## POST /v1/session/summary

上报会话摘要，取回下一步建议。前端节奏是每 5–10 秒一次，或由事件触发。

请求体 `CloudSummary`，响应 `200` 为 `CloudActionEnvelope`。两者都由
`contract.yaml` 生成，字段定义看生成物，不要在这里抄一份会过期的副本：

| 侧 | 文件 | 来源 |
|---|---|---|
| 前端 | `software/app/js/protocol.js` | `protocol/generated/protocol.js` |
| 后端 | `software/backend/app/protocol.py` | `protocol/generated/protocol.py` |
| 校验 | `protocol/schemas/cloud_summary.json`、`cloud_action.json` | `gen.py` |

要加字段就改 `contract.yaml` 再跑 `python3 protocol/tools/gen.py`，**不要手改
生成物，也不要只在一侧加**。

`CloudActionEnvelope.action` 可以为 `null`，表示这一轮只说话、不动设备。
`action.set_level` 越界或与当前状态冲突时，**下游直接丢弃整个 `action`，不钳位**——
把 99 悄悄改成 8 去执行，比拒绝危险得多。台词保留：建议档位不可信不代表
这句话不能说。

## 错误与降级

| 情况 | 后端行为 | 前端必须的行为 |
|---|---|---|
| 请求体不合 schema | FastAPI 返回 `422` | 当作本轮无建议，继续正常运行 |
| 模型超时或失败 | 返回可用的兜底 envelope，不要 `5xx` | —— |
| 云端不可达 | —— | 静默降级，界面照常可用 |
| 建议档位越界 | `moderation` 丢掉 `action` | 安全总督再判一次，不信任云端已经判过 |

前端不重试。这条链路每 5–10 秒就有下一次机会，重试只会在云端已经出问题的
时候加重它。

## 鉴权

**目前所有接口都是裸的，没有任何鉴权。** 这在当前形态下的边界是：后端只监听
回环或可信局域网，用于 demo 与联调。任何把它暴露到公网的部署都必须先补鉴权——
这不是"以后优化"，是上线前的阻塞项。

## 站点用 HTTP 还是 HTTPS，会影响前端能用哪条设备通道

这一条看起来是部署细节，实际会决定前端功能可用性，所以写在这里：

- Web Bluetooth 要求安全上下文。手机浏览器访问 `http://<PC 局域网 IP>:8000`
  不是安全上下文，**蓝牙通道不可用**。
- 玩具侧没有 TLS，只能提供 `ws://`。一旦站点上了 HTTPS，
  **WiFi 备用通道会被浏览器按混合内容拦掉**。

也就是说在手机浏览器里，这两条设备通道**不可能同时可用**。Android 壳没有这个
矛盾（`usesCleartextTraffic="true"` + 原生 GATT 桥），所以 WiFi 备用通道以
Android 壳与桌面 Chrome 为主要验证路径。细节见 [`wifi_ws.md`](wifi_ws.md)。

改变站点的 TLS 配置前，请先想清楚它会关掉哪条通道。

## 版本

这条链路**没有独立版本号**，跟着 `contract.yaml` 的版本走。当前 `0.3.0-demo`。

与设备链路不同，前端不校验后端的协议版本：前后端总是同批部署，而且这条链路
上没有"必须成功"的请求，版本不匹配的后果是收不到有用建议，不是安全问题。
设备链路要卡主版本，是因为那条线上跑着停机指令。
